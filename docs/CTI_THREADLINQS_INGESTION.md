# Sentinel Atlas: проект интеграции Threadlinqs

Статус: DESIGN / NOT VERIFIED в Sentinel Atlas. Только проектирование, без кода,
миграций, включения внешнего доступа или развёртывания правил.

Нормативные основания: [TECHNICAL_SPECIFICATION.md](../TECHNICAL_SPECIFICATION.md)
§6 (CTI ingestion), §8 (Admiralty), §10–13 (изоляция, inventory, coverage,
hypotheses), §19 (security control plane), а также [AGENTS.md](../AGENTS.md).
Название продукта — Sentinel Atlas; репозиторий — QCBots.

## 1. Граница подтверждённого

Две независимые оценки по отчёту Chief CTI от 2026-11-17:

- **TECHNICAL PoC = PASS**: через подключённый MCP реально выполнены
  `get_started` (live-каталог: 81 инструмент, 25 промптов, server 8.2.0) и
  `health` (`status=ok`, API reachable); аккаунт Purple tier 3. Область PASS —
  доступность сервиса и получение каталога, не реализация ingestion в Sentinel Atlas.
- **SECURITY POLICY APPROVAL = PENDING**: outbound-доступ и использование
  Threadlinqs как CTI-источника не одобрены политикой компании. Технический PASS
  не разрешает внешнюю передачу данных или запуск интеграции.

Это сведения из отчёта команды, а не выполненная здесь повторная проверка.
Схемы аргументов/ответов целевых инструментов, стоимость конкретных вызовов и
end-to-end ingestion остаются **NOT VERIFIED**. Live-вызовы и расход кредитов
для подготовки этого документа не выполнялись. Те же границы отражены в
`docs/INTEGRATION_FEASIBILITY.md`.

Threadlinqs — внешний источник, база Sentinel Atlas — источник истины.
До реализации адаптера зафиксировать версию реального MCP-каталога и схемы трёх
инструментов ниже. Имена в документе заданы задачей; параметры и поля ответов
не выдумываются. Поля в §3 — внутренний проектируемый контракт, не обещание API
Threadlinqs. Неподдерживаемые поля остаются неизвестными с причиной.

## 2. Один CTI-репорт: маршрут вызовов

Предусловия: администратор отдельно согласовал outbound-политику и разрешённый
MCP transport/адрес; аналитик утвердил задание импорта и конечный credit cap.
У подключения нет доступа к QRadar, tenant RAG, логам или базе клиентов.
Секрет подключения хранится в secret store и не попадает в запросы AI/аудит.

| Шаг | Инструмент / действие | Ограничение |
| --- | --- | --- |
| 1 | Локально проверить полномочия, дедупликацию и бюджет | Повторный запуск не создаёт повторный платный вызов |
| 2 | `search_threats` — найти публичный материал по теме | Только когда нет известного идентификатора; ограниченный результат, без автоматической пагинации |
| 3 | Аналитик выбирает одну угрозу/репорт из кандидатов | Не обогащать все результаты поиска; неоднозначный выбор приостанавливает задание |
| 4 | `get_threat_hunting_bundle` — получить материал выбранной угрозы | Один bundle; сохранять исходный материал или доступную ссылку, время и контрольную сумму |
| 5 | `get_cve_intelligence` — точечное обогащение | Только для CVE, явно присутствующей в исходнике, с локальным cache/dedup и в утверждённом лимите |
| 6 | Локальные нормализация и анализ, затем analyst review | Клиентское сопоставление выполняется исключительно внутри Sentinel Atlas |

Если идентификатор уже известен, шаг поиска пропускается. Если CVE нет,
обогащение пропускается. Число CVE-вызовов ограничивается планом задания;
неограниченный fan-out запрещён. Схемы валидируются до отправки по live-каталогу;
несовместимость блокирует вызов, а не включает угадывание параметров.

Отчёт проходит жизненный цикл SPEC §6.3:
`NEW → INGESTED → NORMALIZED → ANALYSIS_PENDING → ANALYZED → QUALITY_REVIEW → APPROVED → ARCHIVED`;
допускается `REJECTED`. Ошибки интеграции и бюджета — отдельный статус задания,
не новый статус отчёта. Неполный ответ сохраняется как неполный staging-артефакт,
не переводится автоматически в `APPROVED`. AI создаёт предложения/черновики через
авторизованный Workbench API; прямого доступа harness к БД нет.

## 3. Provenance, нормализация и Admiralty

Для каждого материала сохранять исходник или ссылку согласно §6.2; для каждого
утверждения сохранять ссылку на точное место в источнике. Время — UTC с timezone,
`collection_date` задаёт принимающий backend, не текст внешнего документа.

| Уровень | Внутренние поля / правила |
| --- | --- |
| Материал | `report_id`, `source`, `source_id`, внешний идентификатор при наличии, canonical URL, `title`, `author`, `publication_date`, `collection_date`, `references` |
| Артефакт | SHA-256 исходных байтов, безопасная локальная ссылка, MIME/размер, версия материала, ссылка на запись БД; доступный URL при невозможности сохранить исходник |
| Получение | `ingestion_job_id`, `correlation_id`, имя инструмента, версия каталога/адаптера, время вызова, очищенный fingerprint запроса, результат, фактические credits если провайдер их сообщает |
| Извлечение | `claim_id`, `report_id`, точный locator (страница/секция/фрагмент), исходная цитата допустимого размера, версия parser/model, исходное значение и нормализованное значение |
| Содержание §6.4 | `threat_actors`, `campaigns`, `target_sectors`, `target_regions`, `malware`, `tools`, `iocs`, `ttps`, `cves`, `attack_patterns`, `victimology`, `confidence` |
| Оценка §8 | `source_id`, `claim_id`, `reliability_rating`, `credibility_rating`, `assessment_reason`, `assessed_by`, `assessment_date`, статус draft/confirmed и история подтверждений |

Не создавать IOC/TTP/CVE без исходного свидетельства или отдельно указанного
подтверждённого источника. Дополнительный CVE-ответ получает собственные source,
claim и provenance, не маскируется под исходный репорт. Неподтверждённая
атрибуция остаётся гипотезой; одно совпадение не доказывает принадлежность актора.

Admiralty — две независимые шкалы, назначаемые источнику и конкретному утверждению:

| Source reliability | Значение | Information credibility | Значение |
| --- | --- | --- | --- |
| A | Completely reliable | 1 | Confirmed by other sources |
| B | Usually reliable | 2 | Probably true |
| C | Fairly reliable | 3 | Possibly true |
| D | Not usually reliable | 4 | Doubtful |
| E | Unreliable | 5 | Improbable |
| F | Reliability cannot be judged | 6 | Truth cannot be judged |

Не назначать фиксированную оценку всему каналу Threadlinqs и не преобразовывать
provider confidence автоматически в A–F/1–6. При отсутствии оснований AI может
предложить F6 с объяснением; аналитик подтверждает оценку. Для credibility 1 нужны
ссылки на независимые подтверждения; перепечатки одного источника не независимы.
Смена оценки версионируется с автором, причиной и временем, без потери истории.

Дедупликация: внешний source/id + версия, canonical URL и SHA-256 помогают
выявлять дубликаты; совпавший контент объединяет ссылки provenance, но не удаляет
происхождение. Изменившийся контент создаёт новую версию. Ключи дедупликации и
cache для приватных материалов всегда включают `client_id`.

## 4. Tenant-scoping и Log Source Types

Публичный CTI может храниться в глобальном каталоге. Клиентские аннотации,
релевантность, asset context, расследования, результаты coverage и гипотезы
всегда принадлежат `client_id`; приватный отчёт не становится глобальным.
Публичность устанавливается политикой/аналитиком, а не ответом модели.

На каждом клиентском API/MCP/RAG-вызове backend проверяет `user_id`, `role`,
`client_id`, `permissions`; отсутствие или подмена client_id приводит к отказу.
Фильтр frontend недостаточен. SQL, retrieval, AI context, cache, очереди,
экспорт и ссылки на артефакты сохраняют tenant scope, включая фоновые задания.
Контекст одного клиента не переиспользуется в заданиях другого.

Глобальные `global_fields`, `field_mappings`, `detection_rules`,
`rule_field_requirements`, `mitre_mappings`, `log_source_types` не дублируются.
Не принимать `client_id` или Log Source Types за доказательство авторизации.
Наличие/поступление телеметрии хранится отдельно в `client_log_source_status`.

Для выбранного клиента сопоставлять требования TTP с реальными Log Source Types
и полями Global QRadar Inventory, затем проверять клиентскую доступность и
свежесть телеметрии. Покрытие: `COVERED`, `PARTIAL`, `NOT_COVERED`, `UNKNOWN`;
при нехватке данных — `UNKNOWN`, с причиной. Отсутствие событий не означает
отсутствие угрозы. Общая установленная rule не доказывает покрытие клиента.
AQL/Sigma — только черновики из существующих полей/mappings и проверенных Log
Source Types; неизвестные поля блокируют генерацию. Для гипотез фиксировать
предпосылки, наблюдаемое поведение, ожидаемые FP и способы их снижения.

## 5. Запрет исходящей передачи клиентских данных

В этой интеграции запрещено отправлять во внешний источник клиентские логи,
payload событий, IP/домены/имена активов из клиентского контекста, `client_id`,
QRadar results, секреты, tenant-аннотации или конфиденциальный внутренний CTI.
Редактура/хеширование клиентского лога сами по себе не дают разрешение на экспорт.

Исходящие аргументы формируются по allowlist из публичной темы, публичного
идентификатора угрозы или CVE из публичного источника. Даже совпавший с публичным
IOC клиентский индикатор не отправляется на основании клиентского события.
Не передавать внешний контекст целиком и не разрешать источнику инициировать
дополнительные вызовы. Тексты/ссылки/инструкции в CTI — недоверенные данные;
никаких исполнения команд, доступа к файлам или произвольного fetch по ссылкам.

Входные материалы проходят ограничения размера/типа и безопасное staging.
Аудит хранит actor, action, resource, client scope при наличии, timestamp,
result и correlation_id согласно §19.5; не хранит токены или сырые клиентские
логи. Аудит приватных действий также изолирован по tenant.

## 6. Required human approval

| Решение | Кто / момент подтверждения |
| --- | --- |
| Внешний доступ | Ответственный за сетевую безопасность до подключения; default deny outbound |
| Импорт и credit cap | Уполномоченный аналитик до запуска ограниченного задания; это разрешение на staging, не на доверие |
| Admiralty и CTI approval | Аналитик на QUALITY_REVIEW перед APPROVED; AI лишь предлагает |
| Hunt Hypothesis, TP/FP | Аналитик явно утверждает каждое решение |
| Trusted Adversary Brain, доверенные знания, глобальная Detection Library | Уполномоченный человек утверждает конкретный diff до записи в доверенное состояние |
| Публикация официального отчёта | Человек подтверждает версию, адресатов и tenant scope до публикации |
| Любые будущие write/response операции | Отдельное явное подтверждение; не наследуется от импорта |

Развёртывание правил в QRadar не входит в MVP (read-only) и не выполняется этим
проектом. Approval привязывается к actor, полномочиям, client scope, версии
артефакта, времени и аудиту. Изменение содержимого аннулирует прежний approval.
Технические staging-записи выполняются только в рамках ранее утверждённого
задания; они не изменяют доверенные знания. AI не подтверждает собственный вывод.

## 7. Credit cap и остановка без retry

Рабочее правило задания: **3 кредита за угрозу**. Это плановая ставка из brief,
не независимо проверенный тариф каждого инструмента. Перед платным запуском
подтвердить стоимость по актуальному каталогу/договору; неизвестная стоимость
блокирует вызов. Не считать `search_threats` и `get_cve_intelligence` бесплатными.

Один репорт по одной угрозе: базовый cap **3 кредита**, дополнительные расходы
требуют нового явного бюджета. Если поиск или CVE-обогащение тарифицируются сверх
bundle, они не запускаются в базовом cap. Cap хранится числом в задании; не задан
или отрицателен — отказ, нулевой cap — без внешних платных вызовов.

Перед каждым вызовом атомарно резервировать его верхнюю оценку стоимости:
`spent + reserved + next_call_max <= approved_cap`. При параллельных заданиях
учитывать общий account cap и лимит задания, чтобы один аккаунт не превышал
бюджет. В журнале различать estimated/reserved/actual; отсутствие actual не
означает нулевую стоимость. Неопределённый исход/timeout сохраняет резерв до
сверки, не вызывает автоматический повтор и не допускает двойное списание.

**HTTP 402/429 — STOP, без retry.** Сохранять код, время, correlation_id и
нечувствительную причину; блокировать оставшиеся вызовы задания и новые вызовы
этого account до ручного разбора. Запрещены автоматические повторы, backoff,
пагинация, обход через другой аккаунт/инструмент и планирование повторного запуска
по Retry-After. Статус задания — halted, материал остаётся черновиком.

Возобновление — новое явно одобренное человеком задание после проверки оплаты/
лимита, сверки списаний, cache/dedup и нового бюджета. Не повторять неопределённый
платный вызов без сверки. Ни один error path не повышает cap автоматически.

## 8. Проверяемые критерии будущей реализации

Эти сценарии — контракт для QA, а не результаты выполненных runtime-тестов.

| Проверка | Наблюдаемый результат |
| --- | --- |
| Известная угроза без CVE | Один bundle; search/CVE не вызываются; provenance сохранён |
| Дубликат/новая версия | Дубликат без нового платного вызова; новая версия сохраняет историю |
| Неизвестные schema/цена/бюджет | Внешних вызовов нет; понятная причина в задании |
| Нет source locator или неподтверждённый IOC | Quality Gate не допускает APPROVED |
| Draft Admiralty, нет подтверждения | Trusted state не меняется; подтверждение сохраняет actor/reason/time |
| Клиент A запрашивает данные B через API/MCP/RAG/cache/export | Отказ на backend, нет данных B, аудит отказа |
| Общая rule, нет свежей телеметрии клиента | Нет необоснованного COVERED; UNKNOWN с причиной при нехватке свидетельств |
| Клиентский лог или prompt injection в аргументах | Ни одного outbound-вызова с клиентским содержимым, секретов в аудите нет |
| Два одновременных вызова при cap 3 | Атомарная резервация не допускает превышения cap |
| Ответ 402 или 429 | Ровно один выполненный вызов; ноль последующих вызовов/retry до ручного разбора |
| Timeout после отправки | Резерв удержан; повтор не отправлен автоматически |
| Публикация/правка доверенного знания без approval | Операция отклонена; версия и tenant проверяются при подтверждении |

Для допуска интеграции нужны реальные схемы/transport, утверждённая сетевая
политика, тарифы/лимиты, реализация и артефакты QA: contract, tenant/security,
budget concurrency и end-to-end проверки. В этом PR эти проверки не выполнялись.
